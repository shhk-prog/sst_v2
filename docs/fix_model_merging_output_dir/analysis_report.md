## 結果の分析と考察

### 1. 全体的な性能低下（トレードオフの発生）
マージされたモデル（Merged）は、5つの全タスクにおいて、個別特化モデル（Expert）よりも精度（Accuracy）が低下しています。
これは、異なるデータ分布を持つ複数のタスクに対してモデルパラメータを統合（マージ）した際に発生する、パラメータ間の干渉（負の転移）による一般的な現象です。しかし、`yelp`（-0.0096）や `rt`（-0.01594）などのタスクでは、性能低下が最小限に抑えられており、モデルマージがある程度効果的に機能していることがわかります。

### 2. IMDB タスクにおける大幅な性能低下（-0.075）の要因
他の4タスクの低下が 1%〜2% 程度に留まっているのに対し、**imdb** タスクでは **-7.5%** と突出して大きな性能低下が発生しています。この原因は、マージ実行スクリプトのパラメータ指定方法とマージアルゴリズムの仕組みにあります。

#### 原因の深掘り：
パイプラインスクリプト `run_model_merging_pipeline.sh` のマージ処理部分では、以下のように引数が指定されています。
- `--pretrained_model_name_or_path`: `models/imdb/checkpoint-1563` （**IMDBのファインチューニングモデル**）
- `--ft_model_name_or_paths`: `models/yelp/...`, `models/rt/...`, `models/sst2/...`, `models/amazon/...` （**残り4タスクのExpertモデル**）

また、マージコード `uncertainty_based_gradient_matching.py` の内部ロジックでは、以下のようなパラメータ更新が行われています。
1. ベースラインモデル（`pretrained_model`、ここでは IMDB モデル）のパラメータを初期値とします。
2. マージ対象として指定された各 Expert モデル (`ft_model`) とベースラインモデルとの差分 `(ft_model - pretrained_model)` を計算し、Hessian重みを掛け合わせて加算します。

#### この構成による影響：
- ベースラインとして扱われている `imdb` は、数式上の `(ft_model - pretrained_model)` という差分計算に含まれません。
- そのため、初期パラメータとしての IMDB に対し、他の4つのタスクの方向へ調整された差分（パラメータ変位量）のみが一方的に加算される形になります。
- 結果として、`imdb` 特有の表現能力が他タスクのパラメータ更新によって最も強く干渉（破壊）され、結果として IMDB タスクにおける性能が著しく悪化してしまったと考えられます。

---

## 改善のためのアプローチ案

1. **完全な事前学習モデル（PLM）をベースとする構成への変更**
   マージのベースライン（`--pretrained_model_name_or_path`）に、個別タスクのファインチューニングモデルではなく、オリジナルの事前学習モデル（例: `roberta-base`）を指定し、マージ対象（`--ft_model_name_or_paths`）に `imdb` を含む5つの Expert モデルすべてを指定することで、各タスクを平等にマージし、特定のタスク（IMDB）が突出して劣化するのを防げる可能性があります。

2. **Hessianのスケーリング係数（scaling_factor_pt, scaling_factors_ft）の調整**
   各 Expert の反映強度を制御する `scaling_factors_ft`（現在は `yelp: 112000`, `rt: 8530`, `sst2: 67349`, `amazon: 180000`）およびベースラインの維持強度 `scaling_factor_pt`（現在は `25000`）のバランスを再調整することで、劣化の度合いを緩和できる可能性があります。

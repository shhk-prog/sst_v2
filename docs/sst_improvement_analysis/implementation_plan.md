# 実装計画: SST-Merge 既存結果の課題分析と改善計画

## 1. 現状分析（なぜ既存手法に比べて特別優れていると言えなかったか）

論文ドラフト（`docs/07_paper/論文.md`）の実験結果データを分析した結果、SST-Merge が Task Arithmetic や TIES 等の単純なベースラインに対して**明確なパレート優位（SafetyとUtilityの両方で勝つ状態）を示せていない**ことが確認できました。

例えば、A5 (RepliQA) + A7 (Safety) の結果において：
* **Task Arithmetic ($\alpha=0.20$)**: Jailbreak 耐性 80.20%, RepliQA 48.79%
* **SST-Merge Interpolation k=5 ($\alpha=0.60$)**: Jailbreak 耐性 81.80%, RepliQA 40.05%

このように、Task Arithmetic の強度を少し下げるだけで、SST-Merge と同等以上の Safety-Utility バランスが出せてしまっています。SST-Merge が理論的に優れているはずの「外科的介入」の効果が数字に表れていないのには、以下の構造的な欠陥（改善点）があると考えられます。

## 2. 改善するところ（3つの根本的改善アプローチ）

SST-Merge の真の優位性を証明するためには、マージ手法そのものだけでなく、「実験デザイン」と「評価方法」を根本から修正する必要があります。

### 改善点①：評価指標の不備（失敗モードの捕捉漏れ）を直す
* **課題**: 既存の評価では、Task Arithmetic が「無害な質問にもすべて回答を拒否する（過剰拒絶）」状態になっていても、Jailbreak 耐性は 100% と高く評価され、RepliQA もある程度のスコアが出てしまっています。つまり、ベースラインの「見せかけの高スコア（チート）」を許しています。
* **改善策**: 
    1. **過剰拒絶ベンチマーク（XSTest等）の導入**: 安全な質問に対する False Positive（拒絶してはいけないものを拒絶した割合）を測定し、ペナルティとして厳密に評価します。
    2. **LLM-as-a-Judge (GPT-4o) による推論能力の採点**: 機械的な ROUGE スコアではなく、意味不明な文字列を出力する「推論崩壊」を検知し、品質として正確に減点する評価パイプライン（`lm-evaluation-harness` や `MT-Bench` ベース）へ移行します。

### 改善点②：タスクペアの「競合（Conflict）の弱さ」を直す
* **課題**: RepliQA や Alpaca といった一般的な指示追従タスクは、Jailbreak パッチ（拒絶パッチ）とパラメータ空間での「競合」が比較的小さく、単純な足し算（Task Arithmetic）でもあまり壊れません。これでは SST-Merge の真価（競合を避ける能力）が発揮されません。
* **改善策**: Safety パッチと激しく衝突し、単純マージでは確実に性能が崩壊する「**脆いタスク（Sensitive Tasks）**」を Utility 側に選定します。
    * **金融・医療などの特定ドメイン知識（FinGPT / FPB）**
    * **数学・論理推論・コーディングタスク（GSM8K / MetaMath）**
    これらを用いることで、Task Arithmetic は急激な Utility 劣化（L字カーブ）を描き、SST-Merge のみがパレートフロンティアを押し上げる結果を描出しやすくなります。

### 改善点③：FIM推定とマージ実装のノイズを減らす
* **課題**: $N=500$ の対角近似 FIM では、局所的な分散（ノイズ）を拾いすぎており、本当に Safety/Utility のコスパが良い「急所（Top-k）」を正確に選別できていない可能性があります。また、自作スクリプトでのマージ処理にスケーリングのブレがある可能性も否定できません。
* **改善策**:
    1. FIM推定時のバッチ処理や正規化（$\varepsilon$）のチューニングを再評価し、ノイズに対してロバストな指標（または Data-Free SST のベクトル指標の精緻化）を行います。
    2. コミュニティ標準である **Mergekit** などを活用し、ベースライン実装とSST-Mergeのベースライン適用に関する「実装上の不利やバグ」を完全に排除します。

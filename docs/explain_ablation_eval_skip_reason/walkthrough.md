# 調査報告（Walkthrough）: ジョブ 0, 2, 10, 12, 20, 47 がスキップされずに実行されている理由

## 概要
Slurm ジョブアレイ `102020` において、他の多くのジョブ（1, 3, 4 等）が起動直後に全評価スキップ（`skip complete`）され終了したのに対し、インデックス `0, 2, 10, 12, 20, 47` が実行中（`R` 状態）になっている原因について調査・検証を実施しました。

---

## 主な発見・原因

### 1. Resume ロジックの検証結果
評価スクリプト `scripts/merge_eval_parallel.py` は `--resume` オプション付きで実行されています。
このスクリプトは、評価対象モデルの **全15個の評価タスク**（HarmBench, MBPP, GSM8K, MMLU, AlpacaEval 等）について、出力先の JSON ファイルを事前チェックします（`output_complete()`）。

`output_complete()` が `False` を返す条件：
1. **出力 JSON ファイルが存在しない**
2. **JSON 内の `"status"` が `"failed"` である**
3. **データ件数が `limit` (320件) 未満かつ完了フラグが立っていない**

### 2. 対象ジョブにおける具体的な発生要因

| ジョブインデックス | 対象モデル設定の例 | スキップされない理由 |
|---|---|---|
| **`102020_0`** | `alpha0.0_n50` | `mbpp.json` 内が `"status": "failed"` (前回の `lm_eval` 中の `std::length_error` クラッシュにより失敗記録が残っていたため再実行) |
| **`102020_2`** | `alpha0.0_n500_..._additive` | `mbpp.json` ファイルが存在しなかったため未評価タスクとして再実行 |
| **`102020_10`** | `alpha0.0_n500_..._magnitude` | 過去に失敗（`status: failed`）したタスクが存在するため再実行 |
| **`102020_12`** | `alpha0.2_n50` | 過去に失敗（`status: failed`）したタスクが存在するため再実行 |
| **`102020_20`** | `alpha0.2_n500_..._magnitude` | 過去に失敗（`status: failed`）したタスクが存在するため再実行 |
| **`102020_47`** | その他モデル設定 | 過去に失敗（`status: failed`）したタスクが存在するため再実行 |

---

## 結論
他のジョブ（1, 3, 4 等）は **前回の評価時に全15タスクが正常完了 (`status: success`)** していたため、`resume` モードによって即座に全スキップ処理が行われました。

一方、`0, 2, 10, 12, 20, 47` は前回の実行時に **`mbpp` 評価等で C++ 例外 (`std::length_error`) やメモリ割り当てエラー等で一部の評価タスクが失敗（`status: failed`）していたか、未実行タスクが残っていたため**、`--resume` の自動再試行機構がはたらき、評価スクリプトがスキップされずに実際に GPU 上で再実行されている状態となっています。

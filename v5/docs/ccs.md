# SoK: 安全性回復マージ — 監査対象の論文リストと監査表の項目案

2026年11月24日 · @Hiroki Kinoshita

## 目的と選定基準

ASIACCS 2027（第2ラウンド、2026年12月11日締切）のSoK枠に向けて、監査する論文と、各論文から読み取る項目を決める。監査表は20本以上を目標にし、自分たちの論文3本（FLMSEC、DLSP、SAGAI）も同じ基準で監査する。

- **含める論文**
  - 安全性アライメントを保つ、または取り戻す目的でモデルマージを使う手法（データの有無は問わない）
  - 安全性を評価軸に含むマージのベンチマーク・評価研究
  - マージを経由した攻撃（悪意あるモデルの混入、マージでバックドアが入る、など）。脅威モデルの整理に使う
- **含めない（関連研究の節で触れるだけ）**
  - マージを使わない安全性回復（SafeLoRA のような射影、再学習）。比較の軸として数本だけ参照する
  - 安全性を測らない一般のマージ手法（TIES、DARE など）。監査表には入れず、比較手法として扱う
- **確認状況の書き方**: 「確認済み」＝本文を読んで書誌を確かめた。「要確認」＝タイトルと内容は把握しているが、書誌（年・会議）を本文で確かめていない。

## 監査表の項目案

項目は6グループ・23列。落とし穴P1〜P5に対応する列に印（★）を付けた。ここが「既存研究の評価はここが抜けている」というSoKの主張の根拠になる。

### 記入ルール
- 論文に書いてあることだけを記入する。書いていないものは「記載なし」とし、推測で埋めない。「記載なし」の多さそのものが結果になる
- 各セルに根拠の節・表の番号を添える（例：§4.1、Table 3、App. C）
- コードが公開されている場合、判定器と崩壊の扱いはコードも確認し、「本文」「コード」のどちらで確認したかを分けて書く
- 担当者が2人いるなら、★の列だけは2人で独立に記入して一致率を求める（SoKの信頼性の根拠になる）

### 1. 書誌と脅威モデル
| 列 | 記入する値 |
|---|---|
| 書誌 | 著者、年、会議、URL |
| 脅威モデル | (a) 善意の微調整で安全性が落ちる／(b) 悪意あるモデルが混入する／(c) マージ後のモデルへのjailbreak／明示なし |
| 防御側が使えるもの | 安全データ、有害データ、較正データ、ベースモデル、安全モデルのうち必要なもの |

### 2. 手法の分類軸
| 列 | 記入する値 |
|---|---|
| 安全性の信号の出どころ | データなし／較正データ／安全モデル／安全ベクトル（有害化したモデルの差分） |
| 適用の単位 | 全パラメータ／層／ニューロン・座標（マスク）／部分空間 |
| 前提とする構成 | LoRAか全パラメータか、マージするモデルの数 |

### 3. 実験設定
| 列 | 記入する値 |
|---|---|
| ベースモデル | 名前と規模（複数可） |
| ★モデルの系統の一致（P4） | すべて同じベースから／系統の違うモデルを含む／記載なし |
| ★設定の引き継ぎ（P4） | rope_theta、語彙、チャットテンプレートをどのモデルから取ったか／記載なし |
| seedと不確実性 | seed数、標準偏差や信頼区間の有無 |

### 4. 安全性の評価（中心）
| 列 | 記入する値 |
|---|---|
| 安全性ベンチマーク | HarmBench、AdvBench、JailbreakBench、HEx-PHI、SORRY-Bench などと件数 |
| ★有害判定の方法（P2） | 拒否キーワード／HarmBench分類器／Llama Guard／GPTなどのLLM判定／ベンチマーク内蔵の判定／記載なし |
| ★判定器の数と一致の確認（P2） | 判定器の数。人手の判定との一致率（κなど）を報告しているか |
| ★崩れた出力の扱い（P1） | 扱いなし（安全に数えられる）／繰り返しなどの規則で除外／妥当性を別の指標で報告（VRRなど）／その判定の精度まで検証 |
| 過剰拒否 | XSTestなどで測っているか |
| 適応的攻撃 | なし（固定の有害プロンプトのみ）／テンプレート型／GCG・PAIRなどの最適化型 |

### 5. 有用性と比較のしかた
| 列 | 記入する値 |
|---|---|
| 有用性の評価 | ベンチマーク名。専門タスクと一般能力のどちらか |
| ★係数（α）の選び方（P3） | 固定／グリッド探索（何点か）／検証データで選択／テストデータで選択／記載なし |
| ★手法間の比較のそろえ方（P3） | 同じαで比較／曲線全体で比較／注入量や有用性をそろえて比較 |
| 比較した手法 | 比較対象にした手法の一覧 |
| 公開物 | コード、マージ済みモデル、応答データの公開の有無 |

### 6. 実装の忠実さ（v5のV1・V2で追加）
| 列 | 記入する値 |
|---|---|
| ★数値精度（P5） | 重要度（Fisherなど）やマスクの計算精度（fp32／fp16／記載なし） |
| ★手法が意図どおり動いた証拠（P5） | 実際のマスク比率、退化の有無、注入量などを報告しているか／記載なし |

## 自分たちの論文の扱い

3本とも他の論文と同じ列で監査し、引っかかった落とし穴をそのまま書く。最大の注意点は、FLMSECがすでに「妥当性を考慮した評価」を提案していること。P1を新しい発見として書くと、自分たちの既発表と重なる。

| 論文 | 監査で出そうな点（仮。本文で確認して確定する） | SoKでの使い方 |
|---|---|---|
| A1 FLMSEC | P1：VRRを導入したが、妥当性の判定が弱く崩壊を見逃していた（v5の調査で、safety+medicalではSafeMERGE以外の「妥当」な応答がほぼ100%崩壊の疑い）。P2：本文は「HarmBench Classifierで判定」と書くが、表はベンチマーク別の分類器で作られた可能性が高い。P4：系統の違うモデルを混ぜ、rope_thetaが食い違う | SoKは「FLMSECの拡張と自己監査」として位置づける。「妥当性を分けて測るだけでは足りず、その判定の精度まで検証しないと、妥当性を意識した評価でも崩壊を安全と数える」という一段深い主張にする |
| A2 DLSP | P3：係数を0.5に固定。P4：Mistral-7B系でそろっている可能性が高い（ただしv0.1とv0.3が混ざる表があるので確認）。判定方法と崩壊の扱いは表を読んで記入 | 系統がそろった設定の例。P1とP2が系統をそろえても起きるかの検証に使える可能性がある（応答データが残っていれば） |
| A3 SAGAI | P3：safety+mathでは、同じα（0.6）で比べるとSSTがTAより悪く、曲線全体で比べるとSSTが上回る。P5：fp16キャストでFisherがアンダーフローし、テンソルの60.4%でマスクが全1に退化（後半層L24–31は89.3%）。実際にはTAに近い演算になっていた。論文の条件（Llama-3.1-8B、同じベースのLoRA）とv3の条件も違う | 方法としては表の1行にとどめ、優位性は主張しない |

## v5全範囲の検証を踏まえた更新（11月24日）

落とし穴は4つから5つに増え、どれも重み・キャッシュで原因まで確認できた。さらに、落とし穴を取り除くと手法の優劣が入れ替わる例（safety+math）が得られた。

| # | 落とし穴 | v5で確認した事実 | 簡単な検出方法 |
|---|---|---|---|
| P1 | 崩れた出力が「妥当」と数えられる | 系統の違うパターンで、規則ベースの判定を通った応答の89〜100%が文字化け。safety+mathは0.0〜0.4% | 非ASCII比率、空白のない長い文字列、軽量なパープレキシティ |
| P2 | 判定器しだいで結論が逆転する | 文字化けをWildGuardとStrongREJECTは「有害」、HarmBench分類器は「無害」と判定（0%と68%の乖離の正体） | 判定器を複数使い、割れた応答を人手で確認 |
| P3 | 同じαで比べると優劣を誤る | safety+mathのα=0.6ではSSTがTAより悪いが、曲線全体ではSSTがほぼ全域TAを上回る | 曲線全体、または注入量をそろえて比較 |
| P4 | 系統の違うモデルの混合と設定の取り違え | ベースからの相対差分は WizardMath 2.7%、WizardCoder 113.5%、MedAlpaca 154.7%。codeのマージ済み123件すべてでrope_thetaが不一致 | 重みの相対差分とconfig.jsonの照合 |
| P5（新規） | 数値精度で手法が黙って別物になる | FIMをfp16にすると平均79.2%が0になり、60.4%のテンソルでマスクが全部1に退化。SSTは大半でTask Arithmeticと同じ演算になっていた（注入量比の中央値1.000） | マージごとに実効マスク比率・ゼロ率・inf数を記録し、設定値と照合 |

- FLMSECの行の修正：FLMSECのcodeとmedicalの結論は、系統の違うモデルの崩壊（P1、P4）と判定器の食い違い（P2）の上に成り立っている。SSTの行はP5で本来のSSTとして動いていない。SAGAIの数値はv1（Llama-3.1、LoRA）由来で、v3の不具合とは別。**v1のコードでは、FIMをfp16に変換しておらず、マスクもargsortでちょうどk個を選ぶため、P5の退化は起きないことを確認済み（11月24日）。P5はv3だけの現象。**

## 「直すと結論が変わる」事例（SoKの実証の節の核）
- 既存の応答に拡張した妥当性判定を当て直し、各手法のVRRとConditional ASR、順位がどう変わるかを示す（GPU不要）
- safety+mathでSSTをfp32のマスクでマージし直し、崩れた版と比べる（fp32のFIMは既にあるので、必要なGPUは生成と評価だけ）
- 人手の判定200件で、拡張した妥当性判定と3種類の有害判定器の精度を測る

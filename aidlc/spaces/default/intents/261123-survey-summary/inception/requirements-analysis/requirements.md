# 要件定義：大規模調査のまとめ

## 意図の分析

依頼は「大規模調査のまとめ」である（意図ステートメント `ideation/intent-capture/intent-statement.md`）。FLMSEC 論文に使った v3 の大規模調査の結果（`v3/results/vllm`）を再分析して、secure merge に適した要素を抜き出し、その結果をもとに secure merge（提案論文 DLSP_hiromi2）に組み込む新しい merge 手法の設計案を出すことが目的である。既存の提案手法 SST-Merge は、この大規模調査で他の merge 手法との差を出せなかった。その理由を理論と実験の両面から考察することも含む。

目的は既存手法のランキングではなく、DLSP_hiromi2 に組み込むべき設計要素の抽出である。新しい実験は行わないため、言えるのは新手法が既存手法より優れている「可能性」までである。

既存コードの調査（`aidlc/spaces/default/codekb/v3/` の `business-overview.md`、`architecture.md`、`code-structure.md`）から、次の前提を引き継ぐ。

- 論文 DLSP_hiromi2 は secure merge の提案、SST-Merge はその secure merge に特化した merge 手法、SAGAI_EN_sst は SST-Merge の提案論文、FLMSEC は大規模評価の論文（SST-Merge は載せていない）である。
- SAGAI_EN_sst の数値を出した実装は v3 ではなくリポジトリ外の `v1/` にあり、v3 の結果とは対応しない。v1・v2 は照合のために読んだだけで、本調査の主対象ではない。
- 評価は 4 つの merge パターン、α の 6 点（0.0〜1.0 の 0.2 刻み）、セキュリティ 1 タスク（4 ベンチマーク）、特化 3 タスク（math、code、medical）からなる。
- `v5/` はこれから新設するフォルダで、まだ存在しない。

## 機能要件

### FR1 「secure merge に適した要素」の判定（Validity-constrained Pareto 比較）

比較の方法と、優れた要素の採用基準を分けて定義する。依頼者の回答（質問 Q1）による。

- **FR1.1** レポートの冒頭に、比較の方法（FR1.2〜FR1.5）と、要素を「適した要素」と呼ぶ採用基準を別々に書く。
- **FR1.2** 生成の妥当性を満たすモデルに限定して比較する。主制約は VRR ≥ 80% とし、感度分析として 90% と 50% の場合も併記する。この 3 つの値は、コード生成の前に固定する（丸い基準値と感度分析で、結果を見た後の調整を避ける）。依頼者は FLMSEC の表をすでに見ているので、その事実をレポートに明記する。下限を満たさずに比較から外したモデルの一覧も示す。
- **FR1.3** 安全性は Conditional ASR を主軸とし、ASR と VSR を併記する。各指標の定義と大小の向きは FLMSEC 論文に従う。主軸の有害判定は、論文の定義である HarmBench Classifier 単独（`harmbench_cls_output == "Yes"`）に統一する。`generate_flmsec_hyo.py` の OR 判定（HarmBench 分類器と各ベンチマーク分類器）は、FR3.1 の再現確認でのみ併算する。
- **FR1.4** 有用性は特化性能 3 タスク（math、code、medical）を個別に評価する。正規化した総合値は補助としてのみ使う。
- **FR1.5** 優劣は「同等以下の安全リスクで有用性が改善するか」で判定し、改善幅と不確実性も示す。α は 6 点しかなく、意味も手法ごとに違うため、補間で「同じ安全性」を推定しない。主な判定は、観測済みの点の厳密な Pareto 支配関係とする。補助として、Conditional ASR の差が ±2.0 pt 以内の点どうしの近傍比較を行い、その範囲内での有用性を比べる。FR1 の採用判定では、General 列（MMLU、IFEval、AlpacaEval2）は補助情報とする。

### FR2 仮説検証（V1〜V11）

`code-quality-assessment.md` の「後続段階で要検証」にある V1〜V11 を検証する。依頼者の回答（質問 Q3）と、承認時の方針による。

- **FR2.1** 仮説ごとに、判定に使う指標と反証条件を、実行より前に定義して記録する。結果を見てから、SST の不振を説明できそうな数値だけを選ぶことをしない。
- **FR2.2** 一括で実行せず、次の順に進める。(1) キャッシュ、設定、既存結果の有無の確認、(2) V1〜V9 の CPU 検証、(3) V10〜V11 の再集計。
- **FR2.3** 各仮説を「支持」「不支持」「判定不能」のいずれかに分類し、根拠となる数値と元ファイルを添える。
- **FR2.4** 検証用スクリプトは CPU 専用・読み取り専用とし、`v5/` に置く。実行の前に、実行するコマンドを依頼者に示して許可をもらう。出力先は `v5/` に限る。
- **FR2.5** v1 に関する確認（V12〜V16）は必須とせず、考察の補足として必要な範囲だけ扱う。

### FR3 `v5/` での表と図の再生成

依頼者の回答（質問 Q2 の B）と、意図ステートメントによる。

- **FR3.1** FLMSEC 論文の主な表（手法 × タスク）を `v5/` のスクリプトで再生成し、論文の表との数値一致を確認する。一致しない箇所は一覧にして理由を書く。FR1.3 の有害判定（HarmBench Classifier 単独）と `generate_flmsec_hyo.py` の OR 判定を両方で計算し、判定の違いによる数値の差は、不一致一覧に別項目として載せる。再現する表には General 列も含める。
- **FR3.2** 手法ごとの safety–utility 曲線を、4 つの merge パターン各 1 枚、計 4 枚で出す。単一ドメインの 3 パターン（safety+math、safety+code、safety+medical）は、対応するタスクをプロットする。`safety+math+code+medical` は、特化 3 タスクを 3 つのサブプロットにして 1 枚にまとめる。
- **FR3.3** SST のアブレーションを、論文と同じ形（k × variant）の表にまとめる。α、k、merge パターンなどの条件をそろえて比較し、k・variant の改善効果と α の変更による効果を混同しない。v3 に結果が無い条件は、別の条件で代用せず `N/A`（空欄）とし、FR3.4 の欠損の一覧に記録する。
- **FR3.4** 表と図ごとに、データ件数、欠損、設定値、元の結果ファイルのパスを記録する。結果が無い条件（FR3.3 の `N/A`）は、欠損の一覧にまとめる。
- **FR3.5** 表再生成スクリプトと、生成した表・図は `v5/` に置く。何を行うフォルダかを `v5/README.md` に明記する。`v3/results/vllm` は読むだけで、書き込まない。

### FR4 SST-Merge が差を出せなかった理由の考察

- **FR4.1** 原因を「FIM 選択の問題」「注入方式の問題」「ハイパーパラメータの問題」に分けて分析する。分析の範囲は、V1〜V11 と、既存の `results/vllm`（アブレーション結果を含む）で検証できる範囲までとする。必要なデータが無い項目、または要因を切り分けられない項目は「判定不能」と書き、FR2 の仮説の結果（支持、不支持、判定不能）を根拠として結び付ける。
- **FR4.2** 考察の根拠になる数値は、`v3/results/vllm` の結果ファイルまで辿れるようにする。
- **FR4.3** 理論面の考察は、SAGAI_EN_sst の定式化と、v3 の実装の違い（`architecture.md` の「論文（SAGAI_EN_sst）とコードの対応表」）を踏まえる。

### FR5 新しい merge 手法の設計案

- **FR5.1** 抜き出した各候補要素を、次の 3 段階に分けて書く。(1) 観測事実（既存結果から直接確認できる性能差）、(2) 機構仮説（FIM、マスク、補間方式などによる説明）、(3) 新手法への示唆（DLSP_hiromi2 に導入する設計と、その未検証部分）。
- **FR5.2** 設計案は文章と擬似コードで書く。DLSP_hiromi2 に導入する設計と、未検証の部分を分けて示す。
- **FR5.3** 新手法が既存手法より優れている「可能性」までを述べる。既存の結果で裏付けられる主張と、新しい実験をしないと確かめられない仮説は分けて書く。

### FR6 成果物の構成

- **FR6.1** 成果物は、Markdown のレポートと、`v3/results/vllm` から表を再生成するスクリプトで構成する。
- **FR6.2** レポートは `v5/docs/<topic>/` に置く。`<topic>` は英語の名前とする。

## 非機能要件

- **NFR1** 再現性：表と図の再生成スクリプトは、同じ入力から同じ出力を作る。乱数を使う場合は seed を固定して記録する。
- **NFR2** 既存結果の保全：`v3/results/vllm`、論文、既存のコードとモデルのファイルの変更は 0 件とする。書き込み先は `v5/` に限る。
- **NFR3** 追跡可能性：レポートに載せる数値は、すべて元の結果ファイルのパスまで辿れる。
- **NFR4** 実行の制約：GPU を使わず、モデルの推論、学習、merge の実行を起動しない。検証と再集計は CPU のみで行う。
- **NFR5** 言語：レポート、README、スクリプトのコメントは日本語で書く（コード、識別子、ファイルパスは除く）。

## 制約

- 新しい実験（GPU ジョブ）、論文本文の書き換え、既存結果の編集は行わない（意図ステートメント）。
- v1 と v2 はリポジトリ `v3` の外にある。主対象にせず、考察の補足として読む範囲にとどめる。
- 検証スクリプトの実行は、実行前に依頼者の許可を得る（FR2.4）。

## 前提

- `v3/results/vllm` に、FR1〜FR3 に必要な結果（4 merge パターン、α の 6 点、SST のアブレーション、4 ベンチマークの安全性指標、特化 3 タスクの指標）が揃っている。揃っていない部分は、FR3.4 の欠損の記録に載せる。
- FLMSEC 論文の表は、`scripts/analysis/generate_flmsec_hyo.py` と同じ集計で作られている。この前提が成り立たない箇所は、FR3.1 の不一致の一覧に載る。
- VRR の下限（80%、感度分析は 90% と 50%）と、Conditional ASR の近傍比較の許容範囲（±2.0 pt）は、依頼者が承認時に決めた値である（FR1.2、FR1.5）。依頼者は FLMSEC の表をすでに見ているので、その事実をレポートに書く。

## 対象外

- 新しい merge 手法の実装と、その実験による評価。
- v1 の追加の逆解析（V12〜V16 を必須の検証とすること）。
- SAGAI_EN_sst の数値の再現。
- 論文 FLMSEC、DLSP_hiromi2、SAGAI_EN_sst の本文の書き換え。

## 未解決の問い

- 正規化した有用性の総合値を、補助としてどの計算で作るか（FR1.4）。レポートの設計時に決める。
- 仮説ごとの判定指標と反証条件（FR2.1）の具体的な値。検証用スクリプトを作る時に、実行前の記録として定義する。

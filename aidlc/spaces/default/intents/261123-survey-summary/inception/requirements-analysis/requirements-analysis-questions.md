## Q1. [研究内容] 「secure merge に適した要素」を判定する物差し

意図ステートメントでは、「適した要素」の判定基準をレポートの冒頭で定義するとしています。どの物差しを主にするかで、
再集計する表と比較の組み合わせが変わります。リバースエンジニアリングで分かったとおり、論文（SAGAI_EN_sst）は
「同じ jailbreak 耐性での有用性」を曲線で比べ、FLMSEC 論文は ASR と validity-aware 指標（Conditional ASR、VRR、VSR）で比べています。

A. 安全性と有用性の曲線（α を動かして、同じ安全性での有用性、または同じ有用性での安全性を手法間で比べる）を主にする
B. FLMSEC 論文と同じ指標（ASR と validity-aware 指標、α=0.6 の主結果）を主にし、曲線は補足にする
C. 両方を同じ重みで扱い、一致する要素だけを「適した要素」と呼ぶ
X. Other (please specify)

[Answer]: X. Validity-constrained Pareto 比較。生成の妥当性を満たすモデルに限定した Pareto 比較を主軸にする。制約条件は VRR が事前設定した下限を満たすこと。安全性は Conditional ASR を主軸とし、ASR と VSR も併記する（各指標の定義と大小の向きは FLMSEC に従う）。有用性は特化性能 3 タスクを個別に評価し、必要に応じて正規化した総合値を補助に使う。優劣は「同等以下の安全リスクで有用性が改善するか」で判定し、改善幅と不確実性も確認する。α は 6 点しかなく意味も手法ごとに違うため、補間で「同じ安全性」を推定せず、観測済みの点による Pareto 支配関係と、安全性の許容範囲内での性能比較を優先する。あわせて、「比較方法」と「優れた要素の採用基準」を分け、最終レポートでは各候補要素を「観測事実（既存結果から直接確認できる性能差）」「機構仮説（FIM・マスク・補間方式などによる説明）」「新手法への示唆（DLSP_hiromi2 に導入する設計と、その未検証部分）」の 3 段階に区別して書く。研究の目的は既存手法のランキングではなく、DLSP_hiromi2 に組み込むべき設計要素の抽出である。

## Q2. [研究内容] `v5/` で再生成する表と図の範囲

「表・safety–utility 曲線の再生成」の具体的な出力を決めます。`results/vllm` には 4 つの merge パターン
（safety+math / code / medical と 3 つ全部）と、α の 6 点（0.0〜1.0 の 0.2 刻み）、SST のアブレーションがあります。

A. FLMSEC 論文の主な表（手法 × タスクの表）を `v5/` で作り直し、あわせて手法ごとの safety–utility 曲線を 1 パターン 1 枚で出す
B. A に加えて、SST のアブレーション（k、additive、層重みなど、論文に近い条件）を論文と同じ形（k × variant）の表にまとめる
C. 曲線だけを出す（表の再生成は後回し）
X. Other (please specify)

[Answer]: B。A に加えて SST のアブレーションを論文と同じ形（k × variant）の表にまとめる。追加条件は次のとおり。4 merge パターンについて、安全性と特化性能 3 タスクの関係を個別に可視化する。SST アブレーションでは α、k、merge パターンなどの条件をそろえて比較し、k・variant の改善効果と α の変更による効果を混同しない。データ件数、欠損、設定値、元の結果ファイルを記録する。FLMSEC の表との数値一致を確認する。可能なら、SST が差を出せなかった原因を「FIM 選択の問題」「注入方式の問題」「ハイパーパラメータの問題」に分けて分析する。

## Q3. [実行環境] 仮説検証 V1〜V11 の実行のしかた

V1〜V9 は、キャッシュした FIM テンソルや merge 済みモデルの `config.json`・safetensors ヘッダを読むだけの確認で、GPU は要りません。
V10〜V11 は既存の結果ファイルの再集計です。新しい実験は行わない方針ですが、CPU だけで動く読み取り専用の確認スクリプトを
`v5/` に置いて実行するかどうかで、結果の出し方が変わります。

A. CPU 専用・読み取り専用のスクリプトを `v5/` に置き、実行する前にコマンドを示して許可をもらう（結果は数値でレポートに載せる）
B. スクリプトは `v5/` に置くだけにして、実行は依頼者が行う（レポートには確認手順と期待する読み方だけを載せる）
C. 実行はせず、コードと設定の読解だけで判定する（V1〜V9 は「未確認」のまま残す）
X. Other (please specify)

[Answer]: A。CPU 専用・読み取り専用のスクリプトを `v5/` に置き、実行前にコマンドを示して許可をもらう。追加条件は次のとおり。V1〜V11 を一括実行せず、まずキャッシュ・設定・既存結果の有無を確認し、次に V1〜V9 の CPU 検証、続いて V10〜V11 の再集計の順で段階的に進める。各仮説を「支持・不支持・判定不能」に分類する。実行前のコマンド承認、入力の読み取り専用、出力先の `v5/` 限定を条件とする。仮説ごとの判定指標と反証条件を実行前に定義し、SST の不振を説明できそうな数値だけを後から選ぶことを防ぐ。
